## 1차 — 정리되지 않은 환경에서의 베이스라인

### 데이터 구성
- 데이터셋: [`k-chan-l/pick_and_place2`](https://huggingface.co/datasets/k-chan-l/pick_and_place2)
- **50 에피소드 / 17,480 프레임 (30fps, 평균 약 11.7초/에피소드)**
- 성공 시연만 수집. **정지(no-op) 데이터 없음.**

### 촬영 방식
- 책상 위에 큐브·컵 외에 잡동사니(공구, 케이블, 문서 등)가 그대로 남아 있는 상태에서 촬영.
- `cam_top` / `cam_wrist` 2뷰, leader 팔로 teleoperation.
- 시연자는 카메라 화면이 아니라 실제 로봇팔을 직접 보면서 조작.

### 학습
- 정책: [`k-chan-l/pick_and_place2_act`](https://huggingface.co/k-chan-l/pick_and_place2_act)
- ACT / ResNet-18 / chunk_size 100 / **batch_size 8** / lr 1e-5 / 100,000 steps / save_freq 10,000
- `image_transforms.enable=false` (이미지 증강 없음)
- 학습 환경: 로봇 제어 PC 로컬 (RTX 3070 Laptop, 8GB)

### 결과
- **성공률 0% — 전 시도 실패.**
- 대표 실패 양상: 큐브가 있는 위치와 무관하게 팔이 특정 궤적을 재생하고 **허공에서 그리퍼를 닫음**(허공 파지). 즉 관측을 보고 목표에 접근하는 것이 아니라 시연 궤적의 평균을 그대로 흉내내는 거동.

### 실패 원인 가설
1. **배경 노이즈** — 잡동사니 때문에 이미지에서 큐브가 차지하는 시각적 비중이 작고, 정책이 큐브 위치라는 실제 원인 변수 대신 배경/궤적 타이밍 같은 상관 변수에 붙어버림 (causal confusion).
2. **표본 부족** — 큐브 위치 분포를 충분히 커버하지 못해 위치 조건부 정책이 아니라 단일 평균 궤적으로 수렴. *다만 에피소드 수 자체는 2·3차와 같은 50개이므로, 부족했던 것은 절대 개수보다 **큐브 위치의 다양성** 쪽일 가능성이 큽니다.*
3. 정지 상태 데이터가 전혀 없어, "지금은 움직이지 않아야 한다"는 행동 자체를 학습할 기회가 없었음.

### 다음 라운드 조치
- 책상을 정리하고 **타겟 물체(큐브, 컵)만** 남긴 상태로 재촬영.
- **정지 데이터 추가** — 다음 3종 상황에서 팔이 움직이지 않는 에피소드를 수집:
  - 컵만 있고 큐브 없음
  - 큐브 없음 (빈 작업공간)
  - 큐브가 이미 컵 안에 들어가 있음 (태스크 완료 상태)

## 2차 — 환경 정리 + 정지 데이터 도입

### 데이터 구성
- 데이터셋: [`k-chan-l/pick_and_place`](https://huggingface.co/datasets/k-chan-l/pick_and_place) ← 숫자 없는 쪽이 2차
- **50 에피소드 / 14,315 프레임 (평균 약 9.5초/에피소드)** — 그중 **정지 데이터 20개 (40%)**, 성공 시연 30개.
- 1차보다 총 프레임이 오히려 줄어든 것은 짧은 정지 에피소드가 40%를 차지하기 때문입니다.
- 정지 데이터는 1차 조치대로 3종 상황(컵만 / 큐브 없음 / 큐브가 이미 컵 안)으로 구성.

### 촬영 방식
- 책상 정리 완료, 큐브와 종이컵만 배치.
- `cam_top` / `cam_wrist` 2뷰, 640×480 / 30fps.
- **시연자가 여전히 카메라 화면이 아닌 실제 로봇팔을 직접 보면서 조작.**
- 에피소드 길이 30초 (`--dataset.episode_time_s=30`), 리셋 5초.

### 학습
- 정책: [`k-chan-l/pick_and_place_act`](https://huggingface.co/k-chan-l/pick_and_place_act)
- ACT / ResNet-18 / chunk_size 100 / **batch_size 16** (1차 8에서 증가) / lr 1e-5 / 100,000 steps / save_freq 5,000
- `image_transforms.enable=false` (이미지 증강 없음)
- 학습 환경: **로봇 제어 PC가 아닌 별도 랩탑** (RTX 4070 추정 — 확인 필요). 1차보다 VRAM 여유가 생겨 batch_size를 8→16으로 올릴 수 있었던 것으로 보입니다.
- 출력 경로가 `outputs/train/act_so101/pick_and_place_b16` 로, 배치 크기를 바꿔가며 비교한 흔적이 남아 있습니다.

### 결과
- **10회 평가 중 2회 성공 (20%)**, 30초 제한.
- 단계별 관찰:
  - **접근**: 큐브 방향으로 근접하는 것까지는 대체로 성공 — 1차의 "허공 파지"는 사라짐.
  - **파지**: 정밀 파지에서 실패가 집중. 근접은 하나 마지막 정렬/그립 타이밍이 어긋나 큐브를 놓침 (근접 오차 / 파지 실패).
  - **파지 후**: 일단 큐브를 잡기만 하면 컵으로 이동해 넣고 원위치 복귀까지 **정상 동작**.
  - **정지**: 큐브가 없으면 움직이지 않음 — 정지 데이터가 의도대로 학습됨.
- 요약: 병목은 **파지 직전 정밀 정렬 단계** 하나로 좁혀짐.

### 실패 원인 가설
1. **(a) 관측-시연 불일치** — 시연자가 카메라가 아닌 실물을 보고 조작했기 때문에, 사람은 깊이/시차/미세 정렬을 눈으로 보정하면서 움직였지만 **그 정보는 정책의 관측(2개 카메라 이미지)에 존재하지 않음**. 정책 입력만으로는 재현 불가능한 시연을 학습시킨 셈이라, 정확한 파지에 필요한 단서가 데이터에 없다.
2. **(b) 이미지-액션 시간 정렬 손상** — 카메라 스트림에 프레임 드랍/지연이 있으면 기록된 이미지와 같은 타임스텝의 액션이 실제로는 다른 시점의 장면에 대응하게 됨. 접근처럼 오차 허용범위가 큰 구간은 버티지만, 파지 직전 수 프레임의 정밀 정렬에서 먼저 무너진다 — 관찰된 실패 분포와 일치.

### 다음 라운드 조치
1. **카메라 스트림 압축 전송** — MJPEG 강제(`fourcc: MJPG`)로 USB 대역폭 문제를 해소하고 실시간성 확보 (→ [setup.md](../setup.md)).
2. **카메라 화면을 보며 시연** — 시연자가 정책과 동일한 관측(`--display_data=true`의 top/wrist 화면)만 보고 조작하도록 변경. 가설 (a) 대응.
3. **체계적 촬영 프로토콜 도입** — 모든 에피소드를 다음 순서로 통일:
   1. 전체뷰(`cam_top`)로 큐브 확인
   2. 손목캠(`cam_wrist`)으로 큐브 확인 후 파지
   3. 전체뷰로 컵 확인
   4. 컵 위로 이동
   5. 놓기
   6. 원위치 복귀
4. **정지 데이터 비율 40% → 20%** 로 축소 — 정지 행동은 이미 충분히 학습되었고, 성공 시연 표본을 늘리는 쪽이 이득.

## 3차 — 촬영 프로토콜 정비 후 재수집

### 데이터 구성
- 데이터셋: [`k-chan-l/pick_and_place3`](https://huggingface.co/datasets/k-chan-l/pick_and_place3)
- **50 에피소드 / 27,147 프레임 (평균 약 18.1초/에피소드)** — 그중 **정지 데이터 10개 (20%)**, 성공 시연 40개.
- 2차 대비 프레임 수가 약 1.9배로 늘었습니다. 정지 에피소드가 절반으로 줄고, 6단계 촬영 프로토콜을 지키면서 에피소드당 시연 길이 자체가 길어진 결과입니다.

### 촬영 방식
- 2차 조치 전부 반영:
  - 카메라 MJPEG 압축 스트림 (`fourcc: MJPG`, 640×480 / 30fps)
  - 시연자가 카메라 화면만 보며 조작
  - 6단계 촬영 프로토콜 준수 (전체뷰 큐브 확인 → 손목캠 확인 후 파지 → 전체뷰 컵 확인 → 컵 위로 이동 → 놓기 → 원위치)
- 에피소드 길이 30초, 리셋 5초.

### 학습
- **학습 중.** 실행한 명령은 [commands.md](../commands.md) 참고.
- ACT / ResNet-18 / chunk_size 100 / **batch_size 16** (2차와 동일) / 100,000 steps / save_freq 10,000 / num_workers 8
- **`image_transforms.enable=true` — 이미지 증강을 처음 켰습니다** (1·2차는 모두 `false`). ColorJitter(밝기·대비·채도·색조), SharpnessJitter, RandomAffine(±5°, ±5% 이동)이 적용됩니다.
- 학습 환경: **SSH로 원격 접속한 RTX 5070 Ti**. 로봇 제어 PC는 데이터 수집과 롤아웃만 담당합니다 (→ [setup.md](../setup.md) 4절).
- `--policy.push_to_hub=false` — 체크포인트가 원격 머신의 `outputs/train/act_so101/pick_and_place3/` 에만 남습니다. 롤아웃하려면 제어 PC로 따로 가져와야 합니다.

> **해석 시 주의 — 이번 라운드는 변수가 두 개입니다.** batch_size를 2차와 같은 16으로 둔 덕분에 배치 크기는 통제됐지만, **촬영 프로토콜 개선**과 **이미지 증강 활성화**가 동시에 들어갔습니다. 3차 성공률이 올라가도 둘 중 어느 쪽 기여인지 이 라운드만으로는 분리되지 않습니다. 분리가 필요하면 같은 3차 데이터셋에 `image_transforms.enable=false`로 한 번 더 학습해 비교하는 것이 가장 싼 방법입니다 (데이터 재촬영 불필요).

## 4차 (계획) — 실패 유형 기반 복구 시연 보강

### 데이터 구성 (계획)
- 3차 데이터셋 + **복구(recovery) 시연 15~20 에피소드**.
- 복구 시연 구성은 3차 롤아웃의 **실패 유형 분포에 비례**해 배분. 예:
  - 근접 오차가 많으면 → 잘못 접근한 상태에서 다시 정렬해 파지하는 시연
  - 파지 실패가 많으면 → 그립이 미끄러진 뒤 재파지하는 시연
  - 파지 후 실패가 많으면 → 이송 중 놓친 큐브를 다시 집어 컵에 넣는 시연

### 촬영 방식 (계획)
- 3차와 동일한 프로토콜. 단, 에피소드를 **실패 상태에서 시작**해 복구 과정을 시연.

### 학습 (계획)
- 새로 처음부터 학습하지 않고, 기존 데이터셋과 합친 뒤 3차 체크포인트에서 **`--resume=true`로 이어서 학습** (→ [commands.md](../commands.md)).

### 기대 효과
- ACT는 성공 궤적만 학습하면 분포 밖(실패 직후) 상태에서 회복하지 못하는 compounding error에 취약. 복구 시연은 실패 상태를 학습 분포 안으로 끌어들여 롤아웃 중 자기 회복을 유도.
